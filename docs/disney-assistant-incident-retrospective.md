# 迪士尼语音助手改造故障与失误复盘

更新时间：2026-09-07  
适用项目：ESP32 喵伴 1.0 整机上的兔朱迪语音助手  
当前仓库基线：`7eecd33`  

## 1. 文档目的

本文记录从佛像语音助手改造成兔朱迪语音助手以来遇到的故障、误判和工作流程失误，供后续定位问题和回归测试使用。

记录遵循以下原则：

- 将“已确认根因”“合理推测”和“尚未确认”明确分开。
- 同一种声音不再被直接认定为同一种故障，必须结合设备日志、服务端事件和复位原因判断。
- 发生 ESP32 端回归时，第一步对照原佛像仓库的实现和最后一个已验证版本。
- 不通过随意调大或调小超时、VAD 阈值等参数掩盖尚未定位的故障。
- 本文不保存 API Key、音色凭证、Wi-Fi 密码等敏感信息。

## 2. 当前已知稳定基线

- 使用已经验证过的本机 ESP-IDF 5.5.4 环境，不重复下载安装 ESP-IDF。
- 开发板串口为 COM7。
- 服务端使用普通用户运行在 18124 端口，不依赖管理员开放 18120。
- 固件保持 ASR → RAG/LLM → TTS 的默认分段架构，不改为端到端 Realtime 对话。
- 唤醒词保持“小明同学”；触摸只负责亮屏和播放待机动画，不触发语音会话。
- 当前开口等待参数：首轮 5 秒、追问 10 秒。10 秒是最长等待窗口，检测到人声后会立即继续，不是固定停顿 10 秒。
- 当前服务端 ASR 超时为 12 秒；回答首包等待为服务端 12 秒、设备端 15 秒；回答音频流读取空闲超时为 8 秒。
- 兔朱迪待机、倾听/思考、说话动画已经分别接入；视频音轨已去除，并按圆屏可视区域裁剪。

## 3. 故障与失误记录

### 3.1 没有优先复用已有开发环境

**现象/失误**：曾开始浅克隆 ESP-IDF，实际上佛像项目已经在本机完成过完整编译和烧录。

**根因**：开始工作前没有先检查历史项目、现有 ESP-IDF 路径和已验证的板型配置。

**处理**：停止重复下载，恢复使用 `D:\Espressif\frameworks\esp-idf-v5.5.4` 和原项目验证过的 ESP-VoCat 构建配置。相关提交：`59be82e`。

**防复发规则**：任何工具链安装或升级前，先检查本机已有环境、原仓库 README、历史构建产物和串口烧录记录。

### 3.2 错误假设 18120 必须由管理员放行

**现象/失误**：公网直连 18120 超时后，曾过早判断需要管理员开放端口或配置 nginx。

**根因**：没有先结合服务器上已有的 18121、18122、18123 普通用户项目检查可用端口模式。

**处理**：改用普通用户可运行的 18124，并支持无 root 的后台部署。相关提交：`c69ef39`。

**防复发规则**：端口问题先做进程监听、同用户既有项目和防火墙实测，再判断是否需要管理员权限。

### 3.3 配网页面长期显示“正在连接”或未反馈成功

**现象**：设备屏幕和开机音正常，手机输入 Wi-Fi 后页面长期显示正在连接；之后设备实际上已经进入 Ready，但页面或提示音没有及时反映。

**已确认问题**：配置 AP/DHCP、显示状态和演示端点曾存在不稳定；设备可能已联网，但手机页面没有形成可靠的成功闭环。

**处理**：恢复配置 AP 的 DHCP，稳定显示和演示端点；检查未提交的 fix 分支并合入有效修复。相关提交：`d4fa133`、`7670892`。

**防复发规则**：配网成功必须同时检查设备获得 IP、服务端设备连接事件和手机页状态，不能只依据提示音。

### 3.4 网络切换后唤醒词没有反应

**现象**：新 Wi-Fi 下页面显示 Ready，但说“小明同学”后画面和语音均无变化；也出现过成功一轮后再次无法唤醒。

**已确认根因**：唤醒监听器在部分初始化/会话退出路径中没有正确恢复；另有 Wi-Fi 事件任务栈配置过小的风险。

**处理**：保证唤醒词触发模块只初始化一次并在会话结束后重新启动监听；拒绝过小的 Wi-Fi 事件任务栈。相关提交：`6654f80`、`e09f53e`、`967f21a`。

**防复发规则**：每次会话结束、网络重连和异常退出后，都要验证唤醒任务仍处于运行状态。

### 3.5 设备流量指向了错误或不可达的服务地址

**现象**：设备能够进入部分状态，但无法完成正常云端会话。

**根因**：设备端使用的演示服务地址与实际可达地址不一致。

**处理**：将设备流量路由到正确的服务端局域网/公开入口。相关提交：`3bae5d7`。

**防复发规则**：烧录前打印并核对固件中的服务地址；联调时分别验证 DNS、TCP、WebSocket 和音频 HTTP 路径。

### 3.6 技术错误提示复用了“咚”声，导致误判为重启

**现象**：设备在回答失败或回答结束后播放“咚”，听起来像重复开机或自动重启。

**根因**：`PROMPT_TECHNICAL_ERROR` 曾复用其他铃声音频，同一个声音承担了开机、追问或技术错误等不同语义。

**处理**：恢复不同会话阶段的独立提示音；技术错误使用简短、可区分的提示，不再复用“咚”。相关提交：`a3409cf`、`498d645`。

**经验**：是否硬件重启必须查看 ESP32 复位原因、启动日志和内存遥测，不能凭声音判断。

### 3.7 唤醒、追问和重讲提示音语义混乱

**现象**：唤醒后的“咚”本应是“请讲”；回答后的追问提示也曾与开机音或错误音混淆。

**根因**：替换角色素材时只关注声音风格，没有完整保留原状态机中每个 prompt 的语义映射。

**处理**：分别保留“请讲”“请继续”“请重讲”和技术错误提示。相关提交：`a3409cf`、`c2b9922`、`498d645`。

**防复发规则**：替换音频资产时，按 prompt ID 核对触发阶段、文案、时长和失败语义，不按文件听感猜用途。

### 3.8 克隆语音末尾被截断

**现象**：“你好我是兔朱迪……”“请讲”“请重讲”等生成音频的句尾被截掉。

**根因**：生成结果末尾没有足够静音，播放或转码边界裁掉了最后的发音尾部。

**处理**：重新生成并在末尾预留静音，再用于设备提示。相关提交：`c2b9922`。

**防复发规则**：所有新 TTS 提示音必须检查首尾波形，并保留固定尾部静音后再转 PCM。

### 3.9 直接加入动画后挤占语音链路内存

**现象**：待机动画或多状态动画接入后，出现唤醒即闪退、一次会话成功后下一次失败等现象。

**已确认风险**：视频缓冲、WebSocket 任务栈、录音/解码和播放缓冲会同时争用 ESP32 内部 RAM；仅看总 PSRAM 剩余量不能代表内部连续内存块足够。

**处理**：将待机视频内存与语音链路隔离，将 WebSocket 任务栈和适合的语音运行时分配迁移到 PSRAM，并保留内部 RAM/最大连续块遥测。相关提交：`6ab521d`、`3346139`、`73f55ae`。

**防复发规则**：新增动画时必须记录 free internal RAM、largest internal block 和复位原因，并至少连续完成三轮语音回归。

### 3.10 对圆屏素材需求理解不完整

**现象/沟通失误**：曾按方形画布讨论素材，而设备实际是圆形可视区域；长方形人物素材还需要以脸部为中心向上裁剪。

**根因**：混淆了视频文件的矩形像素画布和物理屏幕的圆形可视区域。

**处理**：保持编码画布符合屏幕控制器规格，同时把主体放在圆形安全区内；去除视频音轨并压缩为设备支持的 AVI。相关提交：`a639422`、`64ec5e8`。

**防复发规则**：屏幕适配同时核对像素分辨率、物理遮罩、圆形安全区、编码格式、帧率和解码内存。

### 3.11 角色知识和人设回答不自然

**现象**：早期知识库存在错误；朱迪回答其他迪士尼角色时过于生硬地强调“不认识”；多次完整介绍狐尼克身份；知识扩展到 120 字后首包延迟增大。

**根因**：知识检索、角色边界和语言风格约束没有分层；提示词把身份边界写成了机械重复规则；检索片段增大也提高了 LLM 首包处理量。

**处理**：以《疯狂动物城》为朱迪最熟悉的知识域，其他迪士尼故事使用“我听说过”等自然转述；单独约束身份和关系回答，避免每轮重复人物小传。相关提交：`abf413d`、`06898c5`、`1253fe5`、`792ef58`、`1fc6817`、`64b32d2`、`474a090`。

**防复发规则**：知识真实性、角色身份、熟悉度语气和回答长度分别测试；不能只增加知识长度而不做延迟回归。

### 3.12 回答音频 URL/播放链路失败导致会话断开

**现象**：设备成功唤醒、录音和上传，服务端返回 `turn_result` 后 WebSocket 断开，随后播放固定技术错误音。

**已确认问题**：回答音频 URL、首包生成和设备 HTTP 等待之间存在时序及超时不匹配；错误音又让它看起来像开机重启。

**处理**：保留分段 ASR-RAG/LLM-TTS 架构，完善音频 URL 和流式读取处理；服务端等待首个音频块 12 秒，设备端首包等待 15 秒，首包后改用 8 秒流空闲超时。相关提交：`498d645`。

**防复发规则**：服务端超时必须小于设备对应阶段的超时，让服务端先返回明确错误；URL 可以提前建立，但不能把“连接已建立”误当成“已有音频首包”。

### 3.13 播放清理失败时主动重启，放大了单轮故障

**现象**：播放资源回收失败可能把一次会话故障升级为整机重启，造成“咚一声闪退”。

**处理方向**：停止用主动重启兜底，优先安全释放播放资源并重新初始化；保留复位原因和内存遥测，以便识别真正的硬件重启。

**当前结论**：这是稳定性设计问题。后续如果再次听到“咚”，仍必须依据 reset reason 判断，不能默认是内存崩溃。

### 3.14 “请继续”之后前几个字被吞

**现象**：用户听到“请继续”后马上开口，识别结果缺少前几个字，甚至两次“你是谁”被识别成别的内容。

**已确认根因**：录音/VAD 开启时机与语音提示结束边界过近，没有保留足够的开口前音频；短句对丢失首字尤其敏感。

**处理**：追问阶段立即布防，增加语音前滚缓冲并保留检测到起音之前的音频；改进短句 ASR。相关提交：`b976db9`、`921922a`、`456a577`。

**防复发规则**：使用“你是谁”“在哪里”“几点了”等短句做首字完整性测试，并查看服务端保存的原始 WAV，而不是只看 LLM 回答。

### 3.15 方向检测经常只显示“正前方”

**现象**：高德/定位功能联调期间，方向结果经常固定为正前方。

**处理**：稳定唤醒方向检测，并将方向有效性、角度和标签加入遥测。相关提交：`a97f5aa`。

**边界**：高德 Web 服务 Key 可以做地理编码、搜索和路线规划，但不能代替 GPS、手机定位或室内定位硬件直接提供 ESP32 的真实位置与朝向。

### 3.16 ASR 卡住导致一直处于聆听/思考状态

**现象**：设备已唤醒并上传音频，但监视页面没有用户文本，长时间没有回答。

**根因**：ASR 云端调用存在偶发长时间无返回；原佛像版最长可等待 30 秒，看起来像设备一直卡住。

**处理**：为 ASR 增加有界等待和明确的 `asr_timeout` 诊断事件，当前上限为 12 秒。相关提交：`f7adb71`。

**防复发规则**：必须区分 `turn_started`、`audio_uploaded`、`asr_started`、`asr_final/asr_timeout` 四个阶段，不能把没有识别文字直接归因于麦克风。

### 3.17 2026-09-07 “请讲”后无识别的具体事件

**现象**：说“小明同学”并听到“请讲”后，设备似乎一直等待，没有出现识别文字。

**已确认事实**：

- 设备上传了 26 个 Opus 帧、4,894 字节。
- 服务端生成了 1.56 秒、49,964 字节的有效 WAV。
- 录音平均音量约 -34.4 dB，峰值约 -18.4 dB，并非空录音。
- 当次 Qwen ASR 超过 12 秒，被记录为 `asr_timeout`。
- 对同一份 WAV 重试时，777 毫秒识别为“你好”。

**结论**：这是一次 ASR 服务/网络调用的偶发卡顿，不是“请讲”后麦克风没有启动，也与追问等待 5 秒无关。

### 3.18 2026-09-07 追问 5 秒超时事件及误判

**现象**：回答后播放“请继续”，随后较快回到 Ready/Offline，用户无法完成追问。

**事件证据**：一次会话中 `playback_complete` 到 `conversation_end` 约 7.38 秒；期间没有第二轮 `turn_started`。该时长与约 0.98 秒“请继续”提示、5 秒本地 VAD 开口等待及约 1 秒收尾吻合。

**能够确认的结论**：该次设备在 5 秒窗口内没有检测到超过阈值的人声，所以没有开始第二轮上传。

**尚不能确认的部分**：当时没有保存串口 `max_level`，因此不能判断究竟是用户开口与提示重叠、环境/音量波动，还是一次麦克风采样异常。此前 5 秒曾多次成功，不能据此认定 5 秒本身就是根因。

**处理**：将首轮和追问窗口分开，当前首轮仍为 5 秒、追问为 10 秒。相关提交：`7eecd33`。修改后实机追问测试成功。

**本次流程失误**：最初倾向于直接调长参数，没有先证明是哪项改动造成回归。复查显示，当天早先的 `498d645` 只改变回答音频/TTS 超时，未修改麦克风、VAD 或追问录音；`388d5d2` 只修改测试。因此没有证据表明当天早先的代码改动造成了追问 5 秒失效。

**防复发规则**：再次发生时先保存串口的 `max_level`、VAD threshold、armed/timeout 时间以及服务端第二轮事件，再决定是否修改参数。

### 3.19 敏感 API Key 直接出现在聊天中

**现象/风险**：调试期间曾直接在聊天中提供服务端 API Key。

**处理原则**：本文和代码均不记录该 Key，不在日志、命令输出或回复中复述它。

**建议**：演示完成后轮换该凭证；以后通过服务器 `.env`、受限环境变量或秘密管理方式配置，只确认“已配置/未配置”，不显示完整值。

## 4. 以后固定采用的定位顺序

1. **保留现场**：先不要重启设备或服务端，记录发生时间。
2. **确认是否真正复位**：查看 ESP32 reset reason、启动日志、free internal RAM 和 largest internal block。
3. **检查设备状态机**：核对 wake、prompt done、waiting speech armed、VAD level、turn start、record end 和 playback complete。
4. **检查服务端阶段事件**：依次核对 device connected、conversation ready、turn started、audio uploaded、ASR final/timeout、answer ready、playback complete。
5. **检查原始录音**：确认 WAV 时长、字节数、音量和实际内容。
6. **对照原佛像版本**：比较同一状态和同一参数的原实现，不先凭印象重写架构。
7. **最小化修改**：一次只修一个已确认原因，不同时调整多个超时、阈值或内存策略。
8. **回归验证**：至少测试首次唤醒、连续三轮追问、短句首字、长回答、网络重连和再次唤醒。

## 5. 当前仍需观察的事项

- 追问窗口改为 10 秒后已经实机成功，但原 5 秒偶发未检测到语音的底层原因尚未被证明。
- Qwen ASR 存在偶发超过 12 秒的情况，需要通过后续事件频率判断是服务抖动还是网络问题，不能因单次事件立即修改超时。
- 动画和语音并发时仍需长期观察内部 RAM 最大连续块，而不只是总 PSRAM。
- 听到“咚”时必须先看复位原因，持续验证技术错误音与真实开机音已经完全可区分。
