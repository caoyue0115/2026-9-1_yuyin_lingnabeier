# v7 联网与多轮追问设计

日期：2026-07-14
状态：已确认（GPT-5.6 审查修订版）
实施阶段：第一部分

## 1. 目标

本阶段在 ESP-VoCat V1.0、16MB Flash、8MB PSRAM 的 v6 基线上完成三项用户体验改造：

1. 开机用本地钟声提示设备已启动，并根据联网结果播放明确的本地提示音。
2. 最多保存 5 个 Wi-Fi，在家庭网络、办公室网络和手机热点之间自动选择和切换。
3. 一条持久 WebSocket 支持首次提问和最多 3 次上下文追问，正常结束时播放“善哉”。

本阶段不实现回答播放期间的唤醒词打断。回答播放和会话处理期间继续暂停 WakeNet，保持当前稳定行为。打断与 AEC 在第二阶段独立实现。

## 2. 非目标

- 不把回答下行音频迁移到 WebSocket。
- 不改变现有 v5 单轮协议和已部署设备行为。
- 不实现跨唤醒、跨重启或跨设备的长期聊天记忆。
- 不允许 GPIO7 在回答播放期间打断。
- 不在本阶段启用播放期 AEC 或 WakeNet。
- 不把本地提示音更新重新绑定到 SPIFFS OTA。

## 3. 本地音频资源

以下音频使用 16kHz、单声道、16-bit little-endian PCM，并通过 `target_add_binary_data` 嵌入 app 固件：

| 用途 | 文案或来源 | 资源策略 |
| --- | --- | --- |
| 开机钟声 | `barely-noticeable-pulsation_1s.wav` 的 16kHz 版本，现有 `intro_1.pcm` 与其重采样结果逐字节一致 | 复用并嵌入 `intro_1.pcm` |
| 联网成功 | 现有“阿弥陀佛” | 复用已嵌入的 `boot_amitabha_1.pcm` |
| 需要联网 | 当前回答音色合成“请联网” | 新增并嵌入固定 PCM |
| 会话正常结束 | 当前回答音色合成“善哉” | 新增并嵌入固定 PCM |

“请讲 / 请重讲 / 请重试”继续沿用现有资源和行为。新增资源失败不得导致崩溃；播放失败记录结构化日志并继续对应状态机。

所有新增固定提示音都进入 app，因此 app-only OTA 可以更新，不依赖 SPIFFS 分区更新。

钟声资源的规范数据为：源 WAV 实际时长 1.5 秒、SHA-256 `BB032222AC74A67DAABDF81A9A44E5E3ADEC8CF7F7885737FBB1AC0B6871E2A2`；目标 `intro_1.pcm` 为 16kHz、单声道、16-bit LE、48,000 字节、SHA-256 `B9CBE3581350A0A168B57D3C2B6C887099AE11C4B070FB741368CC5EB78CB424`。文件名中的 `_1s` 仅是历史命名，不作为时长断言。

## 4. 启动与联网状态机

### 4.1 启动顺序

1. 固件启动并初始化播放链路。
2. 立即播放一次 1.5 秒钟声。
3. 初始化网络管理器并读取 NVS 中保存的 Wi-Fi。
4. 按下述策略联网。
5. 联网成功后播放一次“阿弥陀佛”，随后初始化触发输入并进入语音待机。

### 4.2 首次联网与启动重连

- 未保存任何 Wi-Fi 时，不等待超时；钟声结束后立即播放一次“请联网”，并开启配网热点。
- 已保存 Wi-Fi 时先扫描，按 SSID 合并同名 BSSID，保留最强 RSSI 的 BSSID，再过滤出当前可见的已保存网络并按 RSSI 从强到弱排序。
- 未扫描到任何已保存网络时，不等待满额预算；扫描结束后立即播放“请联网”并开启配网热点。
- 8 秒是从启动扫描开始计算的单调时钟绝对截止时间，包含扫描、关联、认证和 DHCP；任一步都不得单独重新获得 8 秒。
- 扫描到候选时按排序结果完成第一遍，每个候选先尝试 1 次；仍有预算时再对失败候选完成第二遍。每个候选最多 2 次。
- 8 秒内获得 IP 即视为成功，播放“阿弥陀佛”并进入待机。
- 8 秒预算耗尽后播放一次“请联网”，开启配网热点。

配网热点前缀由 `Miaoban` 改为 `GreenMotive`，完整 SSID 为 `GreenMotive-XXXX`。热点地址继续使用 `http://192.168.4.1`，现有 captive portal 和网页配网流程保持不变。

配网提交必须先验证目标 Wi-Fi 可连接，再写入 NVS。配网成功后关闭热点、切回 STA，获得 IP 后播放一次“阿弥陀佛”。

### 4.3 凭据上限与淘汰

- NVS 最多保存 5 组 SSID 和密码。
- 相同 SSID 再次保存时更新密码，不新增重复项。
- 每次成功获得 IP 后更新该网络的最近成功使用顺序。
- 写入第 6 个不同网络时，淘汰最久未成功使用的网络。
- 不可见的已保存网络不会产生逐个连接等待，只参与后续扫描。

当前 `78/esp-wifi-connect` 的 `ssid_manager.cc` 位于被忽略的 `managed_components`，不得直接修改后依赖本地生成目录。为减少重写风险，第一阶段将当前锁定的 3.1.4 版本 fork 到仓库内受版本控制的 `esp_idf_demo/components/esp-wifi-connect`，保留上游许可证和来源版本，并从 `idf_component.yml` 移除 registry 依赖。网页配网、持久化、排序、连接调度和事件全部使用这个可审查的项目组件；后续升级通过显式 vendor 更新提交完成。

NVS 使用带版本号的新 schema，每条记录包含 SSID、密码、最近成功序号和有效标志。首次启动发现旧 `wifi` namespace 的 `ssid/password...ssid9/password9` 平面键时：

1. 只读解析所有完整旧记录，去重后最多保留 5 项；旧列表靠前项获得较新的初始顺序。
2. 在新的临时 namespace 写入完整记录、schema 版本和校验标志，并 `nvs_commit`。
3. 重新读取并校验成功后，原子设置新 schema 的 active 标志；掉电前旧键始终保持不动。
4. 新版本只在 active 标志有效时使用新 schema，否则回退读取旧键并重新迁移。
5. 本阶段不删除旧键，确保回滚旧 app 后仍能联网；后续稳定版本再单独决定清理。

编译期 `DEMO_WIFI_SSID` 只在“新旧 NVS 都没有凭据”时作为一次性出厂种子写入，不得在每次启动时刷新最近成功顺序、覆盖用户密码或挤掉用户保存的网络。

### 4.4 运行中断网

运行中从已连接状态掉线后：

1. 立即扫描并尝试所有可见的已保存网络。
2. 12 秒内恢复时静默继续，不播放提示音。
3. 12 秒仍未恢复时播放一次“请联网”，但不自动开启配网热点。
4. 以断网时刻为基准，在第 15、30、60 秒的绝对截止点重扫；某次扫描耗时不会顺延后续截止点。
5. 一分钟后每 60 秒按绝对周期重扫一次，持续到恢复或用户主动重配。
6. 本次断网已经播放过“请联网”后，恢复成功播放一次“阿弥陀佛”。

“请联网”每个连续断网事件最多播放一次。恢复成功后才重置该提示标记。添加新网络仍使用正常启动后的 GPIO0 长按 5 秒配网，不改变 ESP32-S3 上电时 GPIO0 的下载模式语义。

运行中断网若发生在语音会话内，该轮按技术故障结束并播放“请重试”；网络管理器继续独立执行后台恢复。

### 4.5 配网边界

Demo 阶段保留 `http://192.168.4.1` 和开放 AP，以降低开发成本，但只允许在无凭据启动或 GPIO0 长按触发后的物理在场窗口内开启，窗口最长 5 分钟。提交成功由服务器端安排延迟关闭 AP，不依赖完成页 JavaScript 调用 `/exit`；若 STA 验证失败，AP 保持或自动恢复到剩余窗口。SmartConfig 在本产品构建中关闭，日志严禁输出 Wi-Fi 密码。

## 5. v6 持久会话协议

### 5.1 兼容边界

- 现有 `/api/v5/realtime/opus-stream` 保持协议和关闭行为不变。
- 新增 `/api/v6/realtime/conversation/opus-stream`。
- 旧固件继续使用 v5；新固件仅在功能开关启用时使用 v6。
- 服务器必须先部署 v6，再发布新固件。

### 5.2 连接生命周期

首次由按键或“小明同学”触发后，板端在播放“请讲”期间并行建立 WebSocket，隐藏 TLS 和 WebSocket 握手延迟。

一条连接承载：

- 1 次首次提问，编号 `turn_index=0`。
- 最多 3 次有效追问，编号 `turn_index=1..3`。
- 最多 4 个有效用户轮次。

回答音频仍通过当前 HTTP 流式下行接口播放。WebSocket 在回答播放和 5 秒追问等待期间保持连接，每 15 秒发送一次 WebSocket transport ping；连续 2 个周期未收到 pong 或任何服务器数据则以 `keepalive_timeout` 关闭。服务器只允许一个 active turn。

### 5.3 消息模型

除最初的 `conversation_start` 外，所有控制消息和服务器事件必须携带 `conversation_id`；所有轮次消息还必须携带 `turn_id` 和 `turn_index`。字段缺失、标识不匹配或事件属于已结束/已取消轮次时，接收方不得把它应用到当前轮。

客户端控制消息：

- `conversation_start`：建立临时会话，携带唯一 `client_conversation_id`、设备、音频格式、协议版本和回答模式。
- `turn_start`：开始一轮，携带 `conversation_id`、`turn_index` 和当前连接内唯一 `turn_id`。
- binary Opus frame：复用现有 framed-v1 二进制封装和 sequence 规则。
- `turn_end`：结束当前轮上行。
- `turn_cancel`：取消当前轮生成或音频消费；第一阶段服务器实现和测试，板端在第二阶段打断功能中使用。
- `conversation_end`：携带正常结束或错误结束原因。

服务器消息：

- `conversation_ready`：回显 `client_conversation_id` 并返回 `conversation_id`。
- `ack`：携带被确认的消息类型；帧 ACK 还携带 `highest_contiguous_sequence`，表示服务器已接收的最高连续帧，不表示 ASR、LLM、TTS 或持久化完成。
- `asr_final`：返回当前轮识别结果。
- `turn_result`：返回当前轮 `session_id`、`audio_stream_url` 和结果状态，但保持 WebSocket 打开。
- `turn_cancelled`：确认资源已取消。
- `conversation_done`：确认会话清理完成。
- `error`：返回稳定错误码和可选错误信息。

未知消息类型不得导致进程崩溃；协议状态非法时返回 `error` 并关闭连接。服务器对总轮次再次强制限制，不能只依赖板端计数。

每个 `turn_start` 将 binary Opus sequence 重置为 0，作用域是 `(conversation_id, turn_id)`。相同 sequence 和相同载荷按重复帧忽略并重发 ACK；相同 sequence 但载荷不同属于 `sequence_conflict` 并关闭会话。服务器限制单帧、单轮累计音频字节、单轮时长和连接总时长，超限返回稳定错误码。

每轮规范状态为 `IDLE -> RECEIVING -> PROCESSING -> RESULT_READY -> PLAYING -> COMPLETED`，取消可从 `RECEIVING/PROCESSING/RESULT_READY/PLAYING` 进入 `CANCELLING -> CANCELLED`。同一连接任何时刻只有一轮不处于终态。`turn_result` 只表示结果和音频 URL 已准备好；板端在 HTTP 音频自然 EOF 且播放队列排空后发送 `turn_playback_complete`，服务器随后发送 `turn_complete`，此时才能开始下一轮。

`turn_cancel` 是幂等请求。服务器收到后设置共享取消令牌、停止生产者、关闭提供商流、清空音频缓冲并等待工作者有界退出；完成上述清理后才发送 `turn_cancelled`。`turn_cancelled` 是取消屏障，屏障之后该轮不得再产生可消费的 `asr_final`、`turn_result` 或音频字节。已发出的迟到事件由板端按 `(conversation_id, turn_id)` 丢弃。取消轮次的音频 URL 此后返回 HTTP 410。

`conversation_end` 可重复发送；服务器最多等待 2 秒完成清理并回复 `conversation_done`，板端超时后强制关闭本地 socket，但仍完成本地资源回收。断线重连不恢复临时 conversation；板端用新 `client_conversation_id` 建立新会话，避免不明确的半会话恢复。

### 5.4 上下文

服务器在当前 `conversation_id` 内保存每个有效轮次的规范化问题、最终或部分回答、状态和 `interrupted` 标志。后续追问的 LLM 输入包含本会话之前的全部问答，最多 3 组历史，不跨连接持久化。单条规范化问题和回答必须设置字符/token 上限，超限截断并记录原因。

配额检查在有效 ASR 文本生成后、启动 LLM 前执行；只有服务端接受该轮进入 `PROCESSING` 时扣减一次。相同 `turn_id` 的重试返回原决定，不重复扣减。ASR 空结果、协议拒绝和处理前取消不扣减；已经进入 `PROCESSING` 后的用户打断保留扣减并记录 `interrupted=true`。

连接正常关闭、技术错误关闭或硬超时后，服务器释放临时上下文、音频队列和任务。每轮音频使用按字节计费的有界队列和明确 backpressure，不允许 `chunks: []` 无界累积；生成工作者必须由会话持有其 task/future，观察共享取消令牌，并在清理路径中 join。日志仅记录允许列表中的截断标识、状态、耗时、大小和错误码，不记录完整问题、回答、URL、设备标识、会话标识或音频内容。

### 5.5 Demo 与客户发布安全边界

Demo/COM4 阶段允许继续使用现有 HTTP/WS 和 `X-Device-Id`，不把 TLS 与设备证书放进第一阶段功能关键路径；但必须保留请求大小/速率上限、短时随机音频 URL、取消后 410、敏感日志禁令和服务端输入校验。

向客户设备批量发布前必须完成独立安全门槛：CA 校验的 HTTPS/WSS、每设备凭据或签名、重放保护、与 device/turn 绑定且短时有效的音频授权。该门槛可以独立 PR 实施，但未完成时不得宣称生产安全或扩大到非受控网络。

## 6. 板端多轮状态机

### 6.1 首次提问

1. 触发后播放“请讲”，同时预连 v6 WebSocket。
2. 使用现有等待开口和 VAD 规则采集首次问题。
3. 上传 Opus，取得 `turn_result`，使用现有 HTTP 下行播放回答。
4. 回答播放完成后立即进入静默追问等待。

首次提问前现有“请讲 / 请重讲 / 请重试”流程保持兼容。

### 6.2 追问窗口

- 回答完全播放并排空输出队列后，静默等待最多 5 秒，只等待用户开始说话。
- 用户在 5 秒内开口即进入录音，不会因 5 秒边界强制截断。
- 开口后沿用当前 VAD：约 700ms 尾部静音结束，单次语音最长约 4 秒。
- 无人开口时立即播放“善哉”，不再额外等待 0.5 秒。
- 无人开口属于正常结束，不播放“请重讲”或“请重试”。

### 6.3 有效轮次与重讲

- 只有 ASR 返回有效文本并开始处理该问题时，才消耗一次追问额度。
- 已检测到语音但 ASR 结果为空时，播放一次“请重讲”，重新开放 5 秒，不消耗额度。
- 每个追问位置最多允许 1 次重讲。
- 重讲后无人说话或仍无有效文本时，播放“善哉”并正常结束。
- 网络、WebSocket、服务器、解码或播放技术故障时播放“请重试”，异常结束，不播放“善哉”。

### 6.4 正常结束

- 任意追问窗口无人开口：立即播放“善哉”。
- 重讲仍无有效内容：播放“善哉”。
- 第 3 次追问回答正常播放完成：静默约 0.5 秒，再播放“善哉”。
- “善哉”播放后发送 `conversation_end`，等待短暂确认，关闭 WebSocket，释放资源并恢复 WakeNet/按键待机。

## 7. 模块边界

实现应保持以下职责分离：

- `app_network`：启动连接、运行时重连、提示事件和状态查询。
- Wi-Fi 凭据策略：5 项上限、最近成功顺序、候选排序和淘汰，不包含 UI 或音频播放。
- prompt arbiter：所有本地提示音的唯一入口，维护单队列、优先级、去重键和可打断属性；网络事件只提交语义事件，不直接播放。
- `cloud_conversation`：v6 WebSocket、每轮上传、保活、取消和关闭，不直接操作麦克风或扬声器。
- conversation controller：追问计数、5 秒窗口、重讲和结束原因。
- `playback_session`：第一阶段即引入的当前回答下行 owner。一个 session 拥有 HTTP 请求、解码、jitter、I2S 输出和共享取消令牌，提供 `start/cancel/join`；`cancel` 和 `join` 幂等，所有子任务都在同一有界清理路径退出。
- 现有 `audio_in`、`audio_out`：继续负责录音/VAD和底层音频输出，不再各自决定回答下载任务生命周期。
- 服务端 conversation session：拥有当前轮 worker/future、取消令牌、有界音频队列、上下文和状态机；存储层只保存有界状态，不拥有后台线程。

第一阶段不得把多轮逻辑继续堆入单个超长 pipeline 函数。第二阶段只能通过 `playback_session_cancel()` 和 conversation controller 事件触发打断，不得再改写 HTTP、解码和 jitter 的所有权。

prompt arbiter 的固定优先级为：技术故障/“请重试” > 配网“请联网” > 会话“请讲/请重讲/善哉” > 联网成功“阿弥陀佛” > 开机钟声。已经开始的会话录音和云端回答不被后台网络提示抢占；网络提示保留一个去重后的 pending 事件，待当前会话结束后仍有意义才播放。相同连续断网事件只允许一个 `need_network:<event_id>` 去重键。

## 8. 错误处理与恢复

- 本地音频播放失败：记录错误，继续目标状态，不重启。
- 启动联网失败：进入配网，不进入 app error 状态。
- 后台断网：只提示一次并持续低频恢复。
- WebSocket 预连失败：播放“请重试”并回到待机，不降级为无上下文的隐式多次连接。
- 回答下行失败：发送 `conversation_end` 的错误原因，播放“请重试”。
- 服务器主动关闭：释放所有板端句柄和任务，播放“请重试”。
- 资源不足：关闭当前会话并回到待机，不留下半开启麦克风、扬声器或 WebSocket。
- 所有取消和关闭路径：先禁止新输入，再设置取消令牌，join owner task，最后释放队列、HTTP、codec 和 WebSocket；任何一步重复执行都安全。

### 9.4 资源预算

在进入 COM4 长时测试前先记录关闭功能的基线，再为“Wi-Fi 重连 + TLS/WS（若启用）+ 录音 + HTTP 解码播放”并发设门槛：内部 RAM 最小空闲和最大连续块不得低于基线实测后确定的安全值，所有任务栈高水位至少保留 25%，PSRAM 不得逐轮单调下降，连续 50 个有效轮次后任务/队列/句柄数量回到基线。具体字节阈值由第一次 instrumented build 的测量值写入实现计划和测试配置，未经测量不得拍脑袋写死。

## 10. 发布与回滚

1. 先部署同时支持 v5 和 v6 的服务器。
2. 用现有 v5 smoke test 确认旧设备不受影响。
3. 在 COM4 烧录第一阶段固件并完成真机验收。
4. 代码审查通过后合并第一阶段 PR。
5. 先做单设备 canary，再扩大 OTA。
6. 回滚时旧固件继续使用 v5；服务器保留 v6 不影响旧设备。

任何新 app 启动时都必须在阻塞式 `app_network_start()` 之前检查 OTA pending 状态并启动本地回滚超时任务。离线业务就绪定义为：NVS 可读、音频链路初始化成功、触发输入可进入待机或配网状态；联网和云端上报不是取消回滚的前置条件。验证成功后的报告可在联网后补发。

第一阶段合并并稳定后，才开始第二阶段唤醒词打断与 AEC。
