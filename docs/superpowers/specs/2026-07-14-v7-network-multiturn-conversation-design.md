# v7 联网与多轮追问设计

日期：2026-07-14
状态：已确认
实施阶段：第一部分

## 1. 目标

本阶段在 ESP-VoCat V1.0、16MB Flash、8MB PSRAM 的 v6 基线上完成三项用户体验改造：

1. 开机用本地钟声提示设备已启动，并根据联网结果播放明确的本地提示音。
2. 最多保存 5 个 Wi-Fi，在家庭网络、办公室网络和手机热点之间自动选择和切换。
3. 一条持久 WebSocket 支持首次提问和最多 3 次上下文追问，正常结束时播放“善哉”。

本阶段不实现回答播放期间的唤醒词打断。回答播放和会话处理期间继续暂停 WakeNet，保持当前稳定行为。打断与 AEC 在第二阶段独立实现。

## 2. 非目标

- 不把回答下行音频迁移到 WebSocket。
- 不改变现有 v5 单轮协议和已部署设备行为。
- 不实现跨唤醒、跨重启或跨设备的长期聊天记忆。
- 不允许 GPIO7 在回答播放期间打断。
- 不在本阶段启用播放期 AEC 或 WakeNet。
- 不把本地提示音更新重新绑定到 SPIFFS OTA。

## 3. 本地音频资源

以下音频使用 16kHz、单声道、16-bit little-endian PCM，并通过 `target_add_binary_data` 嵌入 app 固件：

| 用途 | 文案或来源 | 资源策略 |
| --- | --- | --- |
| 开机钟声 | `barely-noticeable-pulsation_1s.wav` 的 16kHz 版本，现有 `intro_1.pcm` 与其重采样结果逐字节一致 | 复用并嵌入 `intro_1.pcm` |
| 联网成功 | 现有“阿弥陀佛” | 复用已嵌入的 `boot_amitabha_1.pcm` |
| 需要联网 | 当前回答音色合成“请联网” | 新增并嵌入固定 PCM |
| 会话正常结束 | 当前回答音色合成“善哉” | 新增并嵌入固定 PCM |

“请讲 / 请重讲 / 请重试”继续沿用现有资源和行为。新增资源失败不得导致崩溃；播放失败记录结构化日志并继续对应状态机。

所有新增固定提示音都进入 app，因此 app-only OTA 可以更新，不依赖 SPIFFS 分区更新。

## 4. 启动与联网状态机

### 4.1 启动顺序

1. 固件启动并初始化播放链路。
2. 立即播放一次 1.5 秒钟声。
3. 初始化网络管理器并读取 NVS 中保存的 Wi-Fi。
4. 按下述策略联网。
5. 联网成功后播放一次“阿弥陀佛”，随后初始化触发输入并进入语音待机。

### 4.2 首次联网与启动重连

- 未保存任何 Wi-Fi 时，不等待超时；钟声结束后立即播放一次“请联网”，并开启配网热点。
- 已保存 Wi-Fi 时先扫描，过滤出当前可见的已保存网络，并按 RSSI 从强到弱排序。
- 未扫描到任何已保存网络时，不等待满额预算；扫描结束后立即播放“请联网”并开启配网热点。
- 扫描到候选时，每个候选最多连接 2 次，全部候选共享 8 秒总预算。
- 8 秒内获得 IP 即视为成功，播放“阿弥陀佛”并进入待机。
- 8 秒预算耗尽后播放一次“请联网”，开启配网热点。

配网热点前缀由 `Miaoban` 改为 `GreenMotive`，完整 SSID 为 `GreenMotive-XXXX`。热点地址继续使用 `http://192.168.4.1`，现有 captive portal 和网页配网流程保持不变。

配网提交必须先验证目标 Wi-Fi 可连接，再写入 NVS。配网成功后关闭热点、切回 STA，获得 IP 后播放一次“阿弥陀佛”。

### 4.3 凭据上限与淘汰

- NVS 最多保存 5 组 SSID 和密码。
- 相同 SSID 再次保存时更新密码，不新增重复项。
- 每次成功获得 IP 后更新该网络的最近成功使用顺序。
- 写入第 6 个不同网络时，淘汰最久未成功使用的网络。
- 不可见的已保存网络不会产生逐个连接等待，只参与后续扫描。

### 4.4 运行中断网

运行中从已连接状态掉线后：

1. 立即扫描并尝试所有可见的已保存网络。
2. 12 秒内恢复时静默继续，不播放提示音。
3. 12 秒仍未恢复时播放一次“请联网”，但不自动开启配网热点。
4. 随后约在断网后的第 15、30、60 秒重扫。
5. 一分钟后每 60 秒重扫一次，持续到恢复或用户主动重配。
6. 本次断网已经播放过“请联网”后，恢复成功播放一次“阿弥陀佛”。

“请联网”每个连续断网事件最多播放一次。恢复成功后才重置该提示标记。添加新网络仍使用正常启动后的 GPIO0 长按 5 秒配网，不改变 ESP32-S3 上电时 GPIO0 的下载模式语义。

运行中断网若发生在语音会话内，该轮按技术故障结束并播放“请重试”；网络管理器继续独立执行后台恢复。

## 5. v6 持久会话协议

### 5.1 兼容边界

- 现有 `/api/v5/realtime/opus-stream` 保持协议和关闭行为不变。
- 新增 `/api/v6/realtime/conversation/opus-stream`。
- 旧固件继续使用 v5；新固件仅在功能开关启用时使用 v6。
- 服务器必须先部署 v6，再发布新固件。

### 5.2 连接生命周期

首次由按键或“小明同学”触发后，板端在播放“请讲”期间并行建立 WebSocket，隐藏 TLS 和 WebSocket 握手延迟。

一条连接承载：

- 1 次首次提问，编号 `turn_index=0`。
- 最多 3 次有效追问，编号 `turn_index=1..3`。
- 最多 4 个有效用户轮次。

回答音频仍通过当前 HTTP 流式下行接口播放。WebSocket 在回答播放和 5 秒追问等待期间保持连接，每约 15 秒发送一次 WebSocket transport ping。服务器只允许一个 active turn。

### 5.3 消息模型

客户端控制消息：

- `conversation_start`：建立临时会话，携带设备、音频格式和回答模式。
- `turn_start`：开始一轮，携带 `turn_index` 和唯一 `turn_id`。
- binary Opus frame：复用现有 framed-v1 二进制封装和 sequence 规则。
- `turn_end`：结束当前轮上行。
- `turn_cancel`：取消当前轮生成或音频消费；第一阶段服务器实现和测试，板端在第二阶段打断功能中使用。
- `conversation_end`：携带正常结束或错误结束原因。

服务器消息：

- `conversation_ready`：返回 `conversation_id`。
- `ack`：确认上行帧或控制消息。
- `asr_final`：返回当前轮识别结果。
- `turn_result`：返回当前轮 `session_id`、`audio_stream_url` 和结果状态，但保持 WebSocket 打开。
- `turn_cancelled`：确认资源已取消。
- `conversation_done`：确认会话清理完成。
- `error`：返回稳定错误码和可选错误信息。

未知消息类型不得导致进程崩溃；协议状态非法时返回 `error` 并关闭连接。服务器对总轮次再次强制限制，不能只依赖板端计数。

### 5.4 上下文

服务器在当前 `conversation_id` 内保存每个有效轮次的规范化问题和最终回答。后续追问的 LLM 输入包含本会话之前的全部问答，最多 3 组历史，不跨连接持久化。

连接正常关闭、技术错误关闭或硬超时后，服务器释放临时上下文、音频队列和任务。日志可保留现有脱敏观测字段，但不得新增密码、完整凭据或未脱敏敏感信息。

## 6. 板端多轮状态机

### 6.1 首次提问

1. 触发后播放“请讲”，同时预连 v6 WebSocket。
2. 使用现有等待开口和 VAD 规则采集首次问题。
3. 上传 Opus，取得 `turn_result`，使用现有 HTTP 下行播放回答。
4. 回答播放完成后立即进入静默追问等待。

首次提问前现有“请讲 / 请重讲 / 请重试”流程保持兼容。

### 6.2 追问窗口

- 回答完全播放并排空输出队列后，静默等待最多 5 秒，只等待用户开始说话。
- 用户在 5 秒内开口即进入录音，不会因 5 秒边界强制截断。
- 开口后沿用当前 VAD：约 700ms 尾部静音结束，单次语音最长约 4 秒。
- 无人开口时立即播放“善哉”，不再额外等待 0.5 秒。
- 无人开口属于正常结束，不播放“请重讲”或“请重试”。

### 6.3 有效轮次与重讲

- 只有 ASR 返回有效文本并开始处理该问题时，才消耗一次追问额度。
- 已检测到语音但 ASR 结果为空时，播放一次“请重讲”，重新开放 5 秒，不消耗额度。
- 每个追问位置最多允许 1 次重讲。
- 重讲后无人说话或仍无有效文本时，播放“善哉”并正常结束。
- 网络、WebSocket、服务器、解码或播放技术故障时播放“请重试”，异常结束，不播放“善哉”。

### 6.4 正常结束

- 任意追问窗口无人开口：立即播放“善哉”。
- 重讲仍无有效内容：播放“善哉”。
- 第 3 次追问回答正常播放完成：静默约 0.5 秒，再播放“善哉”。
- “善哉”播放后发送 `conversation_end`，等待短暂确认，关闭 WebSocket，释放资源并恢复 WakeNet/按键待机。

## 7. 模块边界

实现应保持以下职责分离：

- `app_network`：启动连接、运行时重连、提示事件和状态查询。
- Wi-Fi 凭据策略：5 项上限、最近成功顺序、候选排序和淘汰，不包含 UI 或音频播放。
- 本地提示播放器：按语义播放嵌入 PCM，不决定网络或会话状态。
- `cloud_conversation`：v6 WebSocket、每轮上传、保活、取消和关闭，不直接操作麦克风或扬声器。
- conversation controller：追问计数、5 秒窗口、重讲和结束原因。
- 现有 `audio_in`、`audio_out`：继续负责录音/VAD和 HTTP 下行播放。

第一阶段不得把多轮逻辑继续堆入单个超长 pipeline 函数；conversation controller 应提供可测试的明确状态和事件接口，为第二阶段打断留出取消入口。

## 8. 错误处理与恢复

- 本地音频播放失败：记录错误，继续目标状态，不重启。
- 启动联网失败：进入配网，不进入 app error 状态。
- 后台断网：只提示一次并持续低频恢复。
- WebSocket 预连失败：播放“请重试”并回到待机，不降级为无上下文的隐式多次连接。
- 回答下行失败：发送 `conversation_end` 的错误原因，播放“请重试”。
- 服务器主动关闭：释放所有板端句柄和任务，播放“请重试”。
- 资源不足：关闭当前会话并回到待机，不留下半开启麦克风、扬声器或 WebSocket。

## 9. 测试与验收

### 9.1 自动化测试

- 5 个凭据上限、相同 SSID 更新、最近成功排序和第 6 项淘汰。
- 可见候选 RSSI 排序、单候选 2 次和 8 秒总预算。
- 运行时 12 秒提示阈值以及 15/30/60/60 秒重扫节奏。
- 每个断网事件只播一次“请联网”，提示后恢复只播一次“阿弥陀佛”。
- 所有新增 PCM 的格式、大小、嵌入符号和 app-only OTA 可达性。
- v6 单连接 1 到 4 个有效用户轮次。
- 上下文顺序、最大轮次、保活、正常关闭、错误关闭和资源清理。
- `turn_cancel` 幂等性和取消确认，即使第一阶段板端尚未调用。
- v5 协议回归测试，证明旧客户端行为不变。
- 0、1、2、3 次追问的结束路径。
- ASR 空结果只允许一次重讲，且不消耗追问额度。

### 9.2 COM4 真机验收

- 无凭据启动：钟声、立即“请联网”、`GreenMotive-XXXX` 热点。
- 有效凭据启动：8 秒内联网并播放“阿弥陀佛”。
- 失效家庭网络和有效手机热点并存：自动连接手机热点。
- 运行中从家庭 Wi-Fi 离开并打开已保存手机热点：自动切换。
- 运行中无候选超过 12 秒：只播一次“请联网”；后台恢复后播一次“阿弥陀佛”。
- 配网提交成功后播放“阿弥陀佛”。
- 完整验证 0、1、2、3 次追问，以及所有“善哉 / 请重讲 / 请重试”路径。
- 验证回答期间 WakeNet 仍暂停，避免第一阶段引入声学并发变化。
- 连续多轮运行检查堆内存、任务栈、WebSocket、HTTP和 codec 句柄无增长。

### 9.3 构建与安全门槛

- ESP-IDF N16R8 正式配置构建通过。
- app 二进制保持在 OTA app 分区内，并记录剩余空间。
- 相关 Python/固件测试通过。
- `git diff --check` 通过。
- 变更文件 gitleaks 扫描通过；既有 vendor/example 命中单独记录。

## 10. 发布与回滚

1. 先部署同时支持 v5 和 v6 的服务器。
2. 用现有 v5 smoke test 确认旧设备不受影响。
3. 在 COM4 烧录第一阶段固件并完成真机验收。
4. 代码审查通过后合并第一阶段 PR。
5. 先做单设备 canary，再扩大 OTA。
6. 回滚时旧固件继续使用 v5；服务器保留 v6 不影响旧设备。

第一阶段合并并稳定后，才开始第二阶段唤醒词打断与 AEC。
